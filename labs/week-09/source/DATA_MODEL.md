# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

## 1. ภาพรวม

ระบบฐานข้อมูลประกอบด้วย 2 ตารางหลักที่มีความสัมพันธ์กันดังนี้:

```
+------------------------+              +------------------------------+
|         users          | 1          * |           requests           |
+------------------------+--------------+------------------------------+
| PK  id (INTEGER)       |              | PK  id (TEXT)                |
|     name (TEXT)        |              | FK  requester_id (INTEGER)   |
|     department (TEXT)  |              |     request_type (TEXT)      |
|     email (TEXT,UNIQUE)|              |     location (TEXT)          |
|                        |              |     details (TEXT)           |
|                        |              |     priority (TEXT)          |
|                        |              |     status (TEXT)            |
|                        |              |     created_at (TEXT)        |
+------------------------+              +------------------------------+
```

- **รูปแบบความสัมพันธ์:** เป็นความสัมพันธ์แบบ **หนึ่งต่อหลาย (One-to-Many: 1:N)**
- **คำอธิบาย:** ผู้ใช้งาน 1 คน (`users`) สามารถสร้างคำร้อง (`requests`) ได้หลายรายการ แต่คำร้องแต่ละรายการจะผูกกับผู้ใช้ได้เพียงคนเดียวเท่านั้น โดยเชื่อมต่อผ่าน `requests.requester_id` ซึ่งเป็น Foreign Key อ้างอิงไปยัง `users.id`

---

## 2. ทำไมต้องแยกเป็น 2 ตาราง

- ลดความซ้ำซ้อนของข้อมูล (Data Redundancy): ไม่ต้องเก็บข้อความชื่อ, ภาควิชา, และอีเมลซ้ำไปซ้ำมาในทุกแถวของคำร้อง ช่วยประหยัดพื้นที่จัดเก็บใน Disk

- รักษาความถูกต้องของข้อมูล (Data Integrity): ป้องกันปัญหาการสะกดชื่อหรือชื่อภาควิชาผิดเพี้ยนไปในแต่ละรายการคำร้อง

## 3. รายละเอียดตาราง

### ตาราง `users`

| คอลัมน์      | ชนิด      | ข้อกำหนด                     | เหตุผลที่เลือก                                                                          |
| ------------ | --------- | ---------------------------- | --------------------------------------------------------------------------------------- |
| `id`         | `INTEGER` | Primary Key, `AUTOINCREMENT` | เป็นเลขลำดับภายในฐานข้อมูล ให้ตารางอื่นอ้างอิงได้โดยไม่ผูกกับชื่อหรืออีเมลที่อาจเปลี่ยน |
| `name`       | `TEXT`    | `NOT NULL`                   | ต้องมีชื่อผู้แจ้งเพื่อแสดงผลและติดต่อ โดยยอมรับชื่อภาษาไทยและช่องว่างได้                |
| `department` | `TEXT`    | `NOT NULL`                   | ใช้แสดงสังกัดและกรองคำร้องตามหน่วยงาน                                                   |
| `email`      | `TEXT`    | `NOT NULL`, `UNIQUE`         | ใช้อีเมลระบุตัวผู้ใช้ และป้องกันการลงทะเบียนอีเมลซ้ำ                                    |

### ตาราง `requests`

| คอลัมน์        | ชนิด      | ข้อกำหนด                                                                                  | เหตุผลที่เลือก                                                                    |
| -------------- | --------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `id`           | `TEXT`    | Primary Key                                                                               | เก็บรหัสที่อ่านรู้เรื่องและมี prefix เช่น `REQ-001` ซึ่งไม่ใช่เลขจำนวนเต็มล้วน    |
| `requester_id` | `INTEGER` | `NOT NULL`, Foreign Key ไป `users(id)`                                                    | เก็บเลขอ้างอิงผู้แจ้งแทนการคัดลอกชื่อและข้อมูลผู้ใช้ลงทุกคำร้อง                   |
| `request_type` | `TEXT`    | `NOT NULL`, `CHECK` ให้เป็นหนึ่งใน 4 ประเภท                                               | เก็บข้อความประเภทคำร้อง และป้องกันค่าที่ไม่อยู่ในรายการที่ระบบรองรับ              |
| `location`     | `TEXT`    | `NOT NULL`                                                                                | เก็บชื่ออาคารหรือสถานที่ ซึ่งมีความยาวและรูปแบบไม่แน่นอน                          |
| `details`      | `TEXT`    | `NOT NULL`                                                                                | เก็บคำอธิบายปัญหาหรือสิ่งที่ร้องขอ ซึ่งเป็นข้อความอิสระ                           |
| `priority`     | `TEXT`    | `NOT NULL`, ค่าเริ่มต้น `normal`, `CHECK` เป็น `normal` หรือ `urgent`                     | ให้คำร้องทั่วไปมีค่าเริ่มต้นที่เหมาะสม และจำกัดระดับความเร่งด่วนให้เป็นค่ามาตรฐาน |
| `status`       | `TEXT`    | `NOT NULL`, ค่าเริ่มต้น `pending`, `CHECK` เป็น `pending`, `in-progress` หรือ `completed` | กำหนดสถานะเริ่มต้นและป้องกันการสะกดสถานะหลายรูปแบบ                                |
| `created_at`   | `TEXT`    | `NOT NULL`, ค่าเริ่มต้นเวลาปัจจุบัน                                                       | บันทึกเวลาสร้างโดยอัตโนมัติ เพื่อนำไปเรียงลำดับหรือแสดงประวัติ                    |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

`users.id` ใช้ `INTEGER` เพราะเป็นเลขลำดับภายในฐานข้อมูลและมี `AUTOINCREMENT` ส่วน `requests.id` ใช้ `TEXT` เพราะต้องเก็บรหัสที่มีตัวอักษรและขีด เช่น `REQ-001` การแยกชนิดช่วยให้แต่ละรหัสมีรูปแบบเหมาะกับหน้าที่ของตน

`CHECK` constraint ยังจำเป็นแม้ API ตรวจข้อมูลแล้ว เพราะเป็นการตรวจที่ฐานข้อมูลอีกชั้นหนึ่ง ทุกช่องทางที่เขียนลงฐานข้อมูลต้องผ่านข้อกำหนดเดียวกัน ไม่ว่าจะเป็น API, สคริปต์ หรือการเพิ่มข้อมูลด้วย SQL โดยตรง จึงช่วยรักษาความถูกต้องเมื่อมีโค้ดฝั่ง API ผิดพลาดหรือมีช่องทางใหม่ในอนาคต

นอกจากนี้ `FOREIGN KEY` ป้องกันไม่ให้คำร้องอ้างถึง `requester_id` ที่ไม่มีใน `users` และ `NOT NULL` ป้องกันการบันทึกข้อมูลสำคัญที่ไม่มีค่า ข้อกำหนดเหล่านี้ทำให้ฐานข้อมูลรักษาความถูกต้องได้เอง ไม่ได้พึ่งการตรวจจากหน้าจอเพียงอย่างเดียว

## 5. ตัวอย่างการใช้ JOIN

คำสั่งนี้เชื่อม `requests.requester_id` กับ `users.id` เพื่อแสดงชื่อผู้แจ้งในแต่ละคำร้อง:

```sql
SELECT r.id,
	   u.name AS requester,
	   r.request_type AS type,
	   r.priority,
	   r.status
FROM requests AS r
JOIN users AS u ON r.requester_id = u.id
ORDER BY r.id;
```

ผลที่ได้จาก `campus.db`:

| id      | requester        | type              | priority | status      |
| ------- | ---------------- | ----------------- | -------- | ----------- |
| REQ-001 | สมชาย ใจดี       | แจ้งซ่อม          | urgent   | pending     |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ | normal   | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ     | ขอใช้อุปกรณ์      | normal   | completed   |
| REQ-004 | สมชาย ใจดี       | แจ้งซ่อม          | urgent   | pending     |
| REQ-005 | ปรียา ขยันยิ่ง   | อื่น ๆ            | normal   | pending     |
| REQ-006 | สุภาวดี รักเรียน | แจ้งซ่อม          | normal   | pending     |
| REQ-007 | ธนกฤต ตั้งใจ     | บริการบัญชีผู้ใช้ | urgent   | in-progress |
| REQ-008 | ปรียา ขยันยิ่ง   | ขอใช้อุปกรณ์      | normal   | completed   |

ได้ผลลัพธ์ 8 แถว ครบทุกคำร้อง โดยชื่อผู้แจ้งมาจากตาราง `users` ไม่ได้เก็บซ้ำใน `requests`

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

ใน Week 07 API ส่งข้อมูลคำร้องเป็น JSON object โดยมี `requesterName` เช่น:

```json
{
  "id": "REQ-001",
  "requesterName": "สมชาย ใจดี",
  "requestType": "แจ้งซ่อม",
  "location": "ห้องปฏิบัติการ 301",
  "details": "เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า",
  "priority": "urgent",
  "status": "pending"
}
```

ผลจาก JOIN มีข้อมูลหลักแบบเดียวกัน คือข้อมูลคำร้องพร้อมชื่อผู้แจ้ง แต่ในฐานข้อมูล Week 09 ชื่อผู้แจ้งไม่ได้อยู่ในแถว `requests`; ตารางนี้เก็บ `requester_id` แล้ว JOIN ไปหา `users.name` เมื่อจำเป็นต้องแสดงผล API จึงสามารถแปลงผล JOIN ให้เป็นรูปแบบ JSON ที่ React ใช้ได้

ข้อสังเกตคือรูปแบบสำหรับจัดเก็บกับรูปแบบสำหรับส่งให้หน้าจอไม่จำเป็นต้องเหมือนกัน: ฐานข้อมูลแยกข้อมูลผู้ใช้ออกเพื่อลดความซ้ำซ้อนและรักษาความสัมพันธ์ ส่วน API รวมข้อมูลที่หน้าจอต้องใช้เป็น object เดียว ในตัวอย่าง Week 07 เป็นข้อมูลในหน่วยความจำของเซิร์ฟเวอร์และมี `requesterName` โดยตรง ขณะที่ Week 09 ระบุความสัมพันธ์ด้วย Foreign Key และสามารถดึงชื่อผ่าน JOIN ได้ นอกจากนี้ `department`, `email` และ `created_at` ไม่ได้อยู่ใน object ตัวอย่างของ Week 07 จึงไม่จำเป็นต้องส่งให้ React หากหน้าจอไม่ได้ใช้
