## ผลการทดสอบ SQL Injection

### ① เงื่อนไขที่เป็นจริงเสมอ

* **ยิง:** `GET /api/requests?status=x' OR '1'='1`
* **ผลที่ได้:** `[]` (0 รายการ) ✓ ถูกป้องกัน
* **เพราะ:** ใช้ Parameterized Query (`WHERE r.status = ?`) ค่า `x' OR '1'='1` จึงถูกส่งไปเปรียบเทียบในฐานะข้อความธรรมดา (Literal String) ไม่ถูกนำไปตีความเป็นเงื่อนไข Boolean ทาง SQL ข้อมูลจึงไม่รั่วไหล

---

### ② พยายามลบตาราง (DROP TABLE)

* **ยิง:** `GET /api/requests?status='%3B DROP TABLE requests; --`
* **ผลที่ได้:** `[]` (0 รายการ) ✓ ถูกป้องกัน
* **เพราะ:** ตัวขับเคลื่อน SQLite และ Parameter Binding ปฏิเสธการรันคำสั่งซ้อน (Multiple Statements / Piggybacked Queries) ผ่านพารามิเตอร์ และมองเครื่องหมาย `;` กับ `--` เป็นเพียงตัวอักษรสตริงทั่วไป

---

### ③ ต่อเงื่อนไขเพิ่ม (OR Status)

* **ยิง:** `GET /api/requests?status=pending' OR status='completed`
* **ผลที่ได้:** `[]` (0 รายการ) ✓ ถูกป้องกัน
* **เพราะ:** ระบบนำข้อความทั้งหมดไปค้นหาสถานะที่ตรงกันทั้งประโยค ซึ่งไม่มีคำร้องใดมีชื่อสถานะนั้นจริง จึงไม่เกิดการดึงข้อมูลสถานะ completed ออกมาตามที่ผู้โจมตีพยายามเจาะระบบ

---

### ④ พิสูจน์ว่าตารางยังอยู่หลังการยิงแบบ DROP

* **คำสั่งที่ยิง:** `GET /api/requests` (หรือ `curl http://localhost:3001/api/requests`)
* **ผลที่ได้:** ตอบกลับด้วย HTTP 200 พร้อมรายการข้อมูลคำร้องครบถ้วนตามปกติ ไม่ได้เกิดข้อผิดพลาด `no such table: requests` แสดงว่าตารางยังคงอยู่สมบูรณ์ 100%
